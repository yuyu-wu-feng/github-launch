# GitHub Launch

把项目真实价值编排成容易理解、容易尝试的 GitHub 门面。高 Star 项目提供设计线索；最终结构由当前项目的读者、证据和使用路径决定。

## 先理解，再编排

用户给出项目目录或仓库后直接开始。优先读取项目指引、现有 README、清单与锁文件、入口、核心示例、已有截图、许可证；需要 Release 时再检查版本与变更范围。先定向读取，信息足够就开始写，不为文案遍历整个仓库。

在工作笔记中形成一个简短项目画像，不要求用户填表：

- **读者与场景**：谁在什么情境下需要它？主要读者是使用者、集成者还是贡献者？
- **当前能力**：已经能完成什么？哪些只是计划或实验？
- **最强证据**：哪个真实示例、界面、产物或测量最能说明价值？记录对应文件或来源。
- **首次成功路径**：从获取项目到得到第一个可见结果，需要哪些步骤和前提？
- **采用边界**：平台、依赖、外部服务、费用、权限、成熟度等，哪些会影响是否尝试？

以源码、配置和可复现结果校对旧文档。冲突无法解决时保守描述，别把旧 README 的宣传当成事实。没有仓库或材料时，只索取项目路径、链接或必要描述；只有想法时可写明确标注的草稿，不虚构已实现功能。

## 为项目选择阅读顺序

先判断读者的首要疑问，再选择一种主线；下表是决策线索，不是必须套用的目录。

| 项目与读者 | 通常最先解决的疑问 | 值得前置的内容 |
| --- | --- | --- |
| CLI、自动化脚本 | 能替我完成哪件事？ | 一次真实输入、命令与输出，再给安装 |
| 桌面、移动或 Web 应用 | 用起来是什么样，去哪体验？ | 真实界面、演示或下载入口，再给使用方式 |
| SDK、组件、开发库 | 接入后能写出什么？ | 最小集成示例、依赖与兼容边界 |
| Agent Skill、提示词工作流 | 要交给它什么，最后能拿到什么？ | 可复制的真实请求、输入与产物、完整目录安装方式 |
| 服务、自托管、基础设施 | 我能运行它吗，代价是什么？ | 工作方式、关键前提、最短启动与验证路径 |
| 研究、数据、算法 | 结果是什么，能否复现？ | 有来源的结果、复现入口、数据与评估条件 |
| 已有完整文档站的项目 | 下一步去哪里？ | 清晰定位与少量有效入口，README 可以很短 |

混合型项目选一个主要读者，在必要处提供第二条入口。例如应用下载与库集成分别说明，别把应用专属功能写成 SDK 的能力。早期项目突出已经完成的小闭环，并明确状态。

用一句话向用户说明本次选择的主线，随后直接完成文件，不把大纲审批设为固定环节。需要案例帮助判断时阅读 [参考项目与取舍](references/patterns.md)；通常无需每次重新调研。用户要求最新参考或比较某个仓库时，再核实对应来源。

## 写出简洁而有辨识度的正文

**首屏目标**：让读者迅速知道“它是什么、对我有什么用、下一步怎么试”。标题和一句具体定位之后，按项目特点放最有说服力的证据或行动入口。不要让装饰或目录挤走核心内容。

**亮点来自证据**：优先一个主亮点，必要时补充少量差异。把技术实现翻译为实际收益，再用示例或事实支撑；不要无依据写“最快”“生产级”“零配置”“完全兼容”。没有性能测量就展示操作结果，没有真实截图就用示例，不生成假产品界面冒充实拍。

**快速开始必须闭环**：选择项目实际支持的一条推荐路径，给出必要版本、配置、执行步骤与可观察的成功结果。命令、包名、导入名、端口、环境变量、产物路径均从项目核对。包尚未发布时提供源码运行方式；不要编造包管理器安装命令、下载地址或演示网站。

发布 Skill 时，README 面向使用者，SKILL.md 面向执行任务的 Agent。说明要提供的材料、可以复制的请求、可得到的文件、运行依赖与已验证范围；安装要保留实际引用的目录。展示真实产物时说明输入与条件，尚无案例就标为用法示意，不把示意包装成效果验证。只有一个技能时，不复制技能合集的索引和社区运营区。

**简约靠取舍**：功能不全量罗列，标题不强制凑齐。安装备选、完整参数、贡献流程等在内容确有需要时链接或折叠。小项目可只保留定位、示例、运行方式和必要边界；复杂项目优先沿用已有文档拆分。精简旧文档时保留迁移步骤、兼容性、限制和必要署名，不为短而丢失信息。

**视觉有作用才使用**：优先项目自己的截图、短演示、真实输出或小型流程图。统一标题层级，短段落，留白充足；表格用于比较，徽章只留可验证且有决策价值的状态。默认不添加徽章墙、Star 曲线、重复横幅、密集 emoji 或巨型目录。不要复制参考项目的标识、口号或整段文案。

**适配 GitHub**：以 GitHub 可渲染的 Markdown 为主，少量必要 HTML；不用依赖脚本或自定义 CSS 的布局。仓库内优先相对链接，图片有替代文本，代码块注明语言，宽表格避免成为核心阅读路径。只有确有必要才增加独立视觉素材。

**语言跟随项目**：优先用户指定语言，其次现有文档与目标读者，均无依据时使用用户当前语言。需要双语时独立文件并互链，不把两套全文逐段堆在一个 README。

## 按请求交付材料

- **只优化 README**：直接更新合适的现有 README，沿用项目命名与目录约定，不附带一套无关发布文件。
- **准备项目发布**：完成 README；在现有发布文档位置或 `docs/github-launch.md` 集中提供可复制的 About 简介、少量准确 Topics、适用的主页链接建议及实际缺失项。About 用一句具体描述，Topics 覆盖用途和生态，不堆热门关键词。未知主页就省略。
- **首次或版本 Release**：仅在请求需要时生成 Release 草稿，按 [Release 编写规则](references/releases.md) 区分首次介绍与版本变更。沿用现有 changelog / release 约定；没有约定时写入 `docs/release-notes.md`，不要为了文案新建发版流水线。

已有 LICENSE 时准确沿用；缺失时在交付说明中提示由所有者选择，不擅自指定许可证。计划、待补素材和未确认项放在交付说明中，不把空链接、虚假徽章或占位章节写进成品。

生成材料本身不代表执行远端发布。若用户已明确要求并授权推送、更新仓库信息或创建 Release，沿用该授权完成相应操作；否则交付本地文件和可复制字段即可。不要因“发布材料”四字自动推送、打标签、创建远端 Release 或改仓库可见性。

## 交付前检查

检查与本次改动相称，不把文案任务扩成全仓审计：

- 每个核心能力与亮点能追溯到项目证据；实验功能、外部服务能力与计划没有混成已实现功能。
- 最短示例在可用环境中验证；不能运行时做静态核对，并准确说明未验证的范围，不声称测试通过。
- 检查修改内容的相对路径、标题锚点、图片和主要外链；缺少网络或预览能力时说明相应检查未完成。
- 检查 Markdown 层级、代码围栏、表格与折叠区域；有预览能力时检查渲染，尤其首屏与图片可读性。
- 回看差异，确认没有删除必要说明、引入空模板或把参考项目特有的能力搬过来。
- 做一次“换名检查”：如果换成另一个项目名也完全成立，就补上本项目的具体场景、输入输出或边界，删掉通用宣传。

最终简短交付：文件链接、本次突出什么及为何这样编排、完成的验证和确实需要用户补充的事项。内部画像与证据笔记不必另存一套文档。
