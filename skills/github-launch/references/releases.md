# Release 编写规则

仅在用户要求首次发布说明、版本更新说明或完整发布包包含 Release 时使用。README 解释长期价值；Release 解释这一次发布给用户带来的变化。

## 先确定事实范围

- 识别首次发布还是已有版本更新。核对用户指定版本、清单、标签与现有发布约定；版本冲突不能自行改号掩盖。
- 有明确起止版本时使用该范围。无明确范围时检查实际标签与发布记录，选择有依据的上一版本到目标提交，不凭日期或“最近若干条提交”猜测。
- 不将未提交、未合并或目标版本之外的能力写入版本变更。首次发布的本地草稿可依据当前已实现内容，但注明草稿对应状态。
- 没有可核实的历史时，只描述当前能力，不声称“修复”“新增”或“提升”。缺少版本号时可先写无版本号的草稿，不擅自创建标签。

## 按用户影响组织

用一两句话解释这次最值得关注的结果。仅保留本次确有内容的部分：关键变化、修复、破坏性变化与迁移、安装或升级、已知问题。

- 首次发布：说明当前可完成的核心任务、最短体验方式与成熟度边界；不要复制整篇 README。
- 版本更新：把提交语言翻译成用户可理解的行为变化，保留必要的 PR / issue 引用；不把自动生成的提交清单当作最终叙事。
- 破坏性变化：明确受影响对象、旧行为、新行为与迁移办法。重要兼容性提示放在前面，不能为了“简洁”隐藏。
- 预览能力：明确实验状态及启用方式，与稳定能力分开。
- 下载与升级：只列确实存在、属于该版本的安装方式或附件。草稿中的预期产物要明确标注尚未上传，不能伪造已发布下载链接。
- 没有内容的栏目直接省略，不写空泛的“体验优化”或“多项修复”。

不要为了发布文案自动创建 LICENSE、CI、包注册配置或社区治理文件。需要这些工作时另按用户范围处理。

## 一手样本与提炼

调研日期：2026-09-22。以下是组织方式参考，未来使用无需依赖这些版本仍为最新。

- [uv Releases](https://github.com/astral-sh/uv/releases)：观察到 0.12.17 将增强、预览能力等区分并关联具体变更。可借鉴按能力状态与用户影响分组；小版本没有某类内容就省略。
- [LocalSend Releases](https://github.com/localsend/localsend/releases)：观察到 v1.18.2 在具体变更之前突出旧版本兼容性与 Windows 签名说明。可借鉴把影响采用和升级的关键信息放在最前面。

这些观察用于改进信息顺序，不要求复刻标题、措辞或条目数量。
